# 09 · 专业调研循环（sa.research/1）

本文件是新研究循环的业务与记录契约。工程工单用于开发框架；研究按问题、证据、反馈和轮次组织，不要求研究者复制工程四件套。旧 G0–G3 仅用于存量兼容。

## 1. 五个工作域

| 域 | 任务 | 产出与回流 |
|---|---|---|
| 立项 scoping | 明确目的、问题、读者、范围、截至日期与回答标准 | 研究约定；实质范围变化形成修订，等待真实批准 |
| 调研 research | 以问题组织检索、取数、补证和覆盖盘点 | 来源与日志、缺口；支持分析或触发讨论 |
| 分析 analysis | 检查口径、反证、冲突、假设，形成有边界的回答 | claim/fact/conflict 与问题回答；不足转补证 |
| 讨论 discussion | 对具体版本提出反馈并决定后续去向 | 补证、再分析、立项修订、呈现或有理由的不变更 |
| 呈现 presentation | 组织内容与视觉表达，渲染并看图检查 | 冻结内容、布局、成品、预览及审查；内容问题返回分析 |

五域不是五个串行状态。不同问题可同时处于不同域。研究轮次结束与发布分开；“当前证据不足以判断”也可以是诚实的阶段回答。新增来源不会自动提高置信度，讨论认可也不是证据。

分析域的内容标准见[13](13-研究分析与论证.md)：关键实验要说明对象、干预、对照、结果及支持结论的推理；多篇文献要重建问题如何推进。呈现反馈若指出“只摆证据、未说清楚”，先建立analysis后续任务，再派生成品，不能只重排版。

## 2. 研究记录与状态

- `research/cycle.json`：schema、project、records。只通过 CLI 追加；当前状态由记录计算。
- `research/artifacts/<id>/<filename>`：冻结的引用材料，按 sha256 校验。工作文件后续改动不影响旧轮次。
- `research/README.md`：导航，不复制当前机器状态。`cycle status` 给当前约定、轮次、问题回答、任务和呈现概览。
- 新项目研究问题、范围与验收口径以 agreement 为唯一权威，project.json 不另存这三项。
- 新项目 `project.json.workflow=sa.research/1`，生命周期为 active/suspended/archived。交付版本单独记录，项目不用 delivered 表达研究问题已全部解决。
- 老项目未标 workflow 时按 legacy 解释；可叠加 research/，原 status、G0–G3 和 waiver 仍按旧规则验证。
- 任意未知 workflow/schema 报错，不自动猜测。历史缺失批准、复核或讨论记为未知，不伪造。

## 3. 事件字段

所有记录：`id`（项目内唯一，小写字母开头，字母/数字/连字符，≤80字符）、`type`、`at`（带时区 ISO 时间；apply 未提供时自动填写）。引用只能指向前序记录，整批 apply 也按顺序解释。

| type | 必填业务字段 | 规则 |
|---|---|---|
| artifact | path, sha256, label | 由 capture 创建，不能用 apply 伪装登记 |
| agreement | question, purpose, audience, scope, out_of_scope[], as_of, acceptance[], status | draft/approved；修订加 supersedes、change_reason |
| question | agreement, text | 稳定问题 ID；换约定时建新问题并显式描述承接 |
| round | agreement, questions[], trigger | 新轮次绑定当前已批准约定，问题必须属于该约定 |
| discussion | round, questions[], author, feedback, materials[], disposition | follow_up/no_change；不变更加 rationale |
| action | round, question, discussion, domain, task, owner | 五域之一；对应同轮讨论中的问题 |
| outcome | action, status, summary, materials[] | done/deferred；延后加 reason；一个任务一个结果，返修建新任务 |
| answer | round, question, status, summary, materials[], limitations[] | answered/partial/insufficient；后两者须有局限 |
| round_close | round, summary, unresolved[] | 所有问题在最新工作后已回答；任务都有结果；反馈都有去向；未决事项显式登记 |
| presentation | round, agreement, content, layout, output, preview, renderer, visual_review | 四个材料字段是 artifact ID；约定与轮次一致；新版本新 ID |

文本字段非空；数组中的条目为非空字符串，允许 out_of_scope/limitations/unresolved 为空，但具体业务约束仍适用。materials 至少一个材料；acceptance 和 round.questions 不为空。

### 批准与修订

approved agreement 需要：

```json
"approval": {
  "actor": "user",
  "statement": "用户实际批准的原话或准确摘录",
  "artifact": "a-user-approval"
}
```

机器检查凭据存在、冻结与字段完整，不验证真实人的身份。代理不得把本人的判断或沉默写成用户批准。研究范围没有变化时继续使用原约定，避免反复索取许可。草案修订可以记录，但不能启动其正式轮次。

### 视觉审查

```json
"visual_review": {
  "status": "passed",
  "viewed": true,
  "reviewer": "manager",
  "mode": "self",
  "notes": "读取本版实际渲染图，检查主次、连线、文字及裁切；本次为自查。"
}
```

status 为 pending/passed/failed。passed/failed 均需实际读图、人员、意见和 self/independent 身份。pending 可只含 status。结构检查不等于视觉通过；视觉自查不等于独立复核。CLI 仅检查登记完整性，不能证明模型实际看过图片。

## 4. 操作协议

```powershell
# 新项目默认新循环；--workflow legacy 可显式使用旧模板
python scripts/sa.py new topic --title "研究主题"

# 老项目叠加，不重写旧状态
python scripts/sa.py cycle init workspace/p-YYYYMMDD-topic

# --file 是项目内工作文件，复制冻结后再引用 ID
python scripts/sa.py cycle capture workspace/p-YYYYMMDD-topic --file brief/approval.md --id a-approval --label "研究范围确认"

# --file 是本机可读 JSON 文件，可为单条或数组；批量失败不部分写入
python scripts/sa.py cycle apply workspace/p-YYYYMMDD-topic --file records.json
python scripts/sa.py cycle status workspace/p-YYYYMMDD-topic
python scripts/sa.py cycle lint workspace/p-YYYYMMDD-topic
python scripts/sa.py lint workspace/p-YYYYMMDD-topic
```

apply 自动校验整本历史及引用材料的哈希；失败保持原文件。写锁拒绝并发写入。异常中断留下锁时，先确认没有正在运行的写者，再处理锁；不得绕过锁并发写入。协议不提供改写历史或删除记录操作。直接编辑磁盘文件不在防篡改保证内，本系统不是签名审计服务。

## 5. 一轮研究的结束

每个问题有最新回答，所有讨论有处理结果或后续任务，任务有结果，暂不可得与未解决事项写清楚。停止原因可以是回答充分，也可以是预算、时间或数据可获得性边界；不能把找不到证据变为不存在的事实。

新证据推翻已结束轮次时，建立新轮次和新结论版本。旧轮次及交付保留。新立项约定不会自动改写旧呈现的范围归属。

## 6. 质量与边界

来源等级、置信度、反证、冲突、数字口径、中立性继续按 03/05 执行。专业复核关注证据是否支撑论断，不由工单进度或成员身份代替。讨论只引用材料版本，不能直接当作 claim 的来源。

新机器记录使用领域中立的责任人字段，不强制研究者采用工程经理、干事、顾问称谓。独立复核的职责分离仍适用。

## 7. 兼容与回退

旧 `docs/01` 和 `docs/04` 原文保留在 `docs/legacy/` 供存量解释。现有证据目录和 public CLI 不变。旧项目 init 只新增 research/；停用此叠加层前保留完整副本，已有新成果引用不能丢弃。新项目不存在可自动恢复的旧 G0 历史；若需旧协议，显式新建 legacy 项目。

此版支持固定画布呈现实验的版本登记，未将实验渲染器升级为所有媒介的通用渲染器。独立新代理验收仍需实际执行，不由文档齐全代替。

## 8. 呈现设计与经验沉淀

设计方法见 [11](11-PPT设计方法与模式.md)。设计意图和视觉修订记录使用现有 artifact/capture，并由 outcome/answer 的 materials 引用；presentation 的四项材料和 schema 保持不变。项目反馈先进入 discussion/action；可迁移方法再经框架工单更新规范与技能，不把业务用户认可等同于证据升级。

## 9. Research IR 与输出快照

调查和分析形成 Research IR；HTML、DOCX、PPT 等输出只消费冻结的 Research Snapshot，不直接读取工作版台账。

```powershell
python scripts/sa.py research-ir build <project> --revision r1
python scripts/sa.py research-ir validate <project> --revision r1
python scripts/sa.py research-ir validate <project> --revision r1 --check-sources
python scripts/sa.py research-ir snapshot <project> --revision r1 --id a-ir-r1 --label "Research IR r1"
```

- Research IR 是来源、研究循环、claim/fact/conflict 和研究叙事的物化投影。
- `analysis/research-ir/` 是工作版，可重建；不是交付依据。
- `snapshot` 通过现有 `cycle capture` 冻结为 artifact，并记录来源文件哈希。
- `validate` 默认只校验快照自身结构；`--check-sources` 另外核对当前工作文件是否仍与快照哈希一致。
- 输出记录必须引用冻结 artifact；工作文件变化不会改写旧输出。
- 内容缺失或口径错误回到调查/分析；输出格式和视觉问题留在对应输出流程。

## 10. 输出登记

`outputs/registry.json` 使用 `sa.outputs/1` 追加输出与审查事件，不修改 `sa.research/1`。

```powershell
python scripts/sa.py output init <project>
python scripts/sa.py output apply <project> --file outputs.json
python scripts/sa.py output status <project>
python scripts/sa.py output lint <project>
```

- `output` 记录绑定约定、轮次、Research Snapshot、请求、计划、可选布局和成品；预览可在登记时提供，也可在后续审查中提供。
- `review` 记录追加实际阅读或看图后的 `pending/passed/failed` 状态；通过或失败必须引用冻结的 `review.preview`，旧记录可用 `output.preview` 兼容。
- output 不可改写；失败、返修和复验分别追加 review，不覆盖旧审查。
- 每种格式使用独立 Plan schema：DocumentPlan、ExperiencePlan、DeckPlan。
- PPT 输出需要 Render Layout；DOCX/HTML 可按适配器需要选择。
- 失败登记整体不写入；输出历史只能追加，新版本新建 output ID。

PPT 可使用统一 Deck 适配器：

```powershell
python scripts/sa.py deck convert <project> --content <content.json> --layout <layout.json> --snapshot <artifact-id> --plan-id <plan-artifact-id> --plan-out <plan.json> --layout-out <render-layout.json>
python scripts/sa.py deck validate <project> --plan <plan.json> --layout <render-layout.json>
python scripts/sa.py deck build <project> --plan <plan.json> --layout <render-layout.json> --output <deck.pptx>
python scripts/sa.py deck preview <project> --pptx <deck.pptx> --out-dir <preview-dir>
```

旧 content/layout LR 只通过转换器进入新格式；转换后的 DeckPlan 必须携带非空
`artifact_id`，并与 RenderLayout 的 `plan` 引用一致。新渲染器不直接依赖项目私有脚本。
