# 01 · 调研治理

> 迁移说明（2026-10-26）：本文件保留旧项目 G0–G3 与治理记录的兼容语义。新方向按五域与反馈循环独立定义，见[专业调研循环](../09-专业调研循环.md)。调研业务不再自动回落到工程治理；工程技能只约束仓级开发。下文角色映射等旧规则在正式迁移前用于解释存量，不代表新模型已定稿。

## 0. 三条不变量

1. **结论属于证据链，不属于任何角色。** 角色可以提出、质疑、否决结论，但不能凭身份让一条无证据的结论成立。
2. **任何工作都有归属。** 框架与规范的演进 → 仓级 `_dev/` 工单；一次调研 → 项目级 `_dev/`；两者都没有的"顺手活"，只能是一行登记级的微修。
3. **原始证据不可变。** 来源一旦入库，只增不改；修正以新来源 + 新 claim 版本表达。

## 1. 角色

| 角色 | 职责 | 可以做 | 不可以做 |
|---|---|---|---|
| **经理**（唯一，当前主代理） | 与用户对接、拍板、阶段门放行、终审 | 拆分子问题、派工、裁定偏离、抽查证据 | 亲自把未进台账的结论写进交付物 |
| **调研干事** | 检索、取数、清洗、分析、写稿 | 在任务书范围内自主选择检索式与工具 | 拍板范围、改动证据分级标准、自审自己的 claim |
| **顾问** | 出方案、给观点、挑战假设 | 读全部材料、提出替代解释、指出逻辑漏洞 | 修改文件、执行交付、参与初审 |
| **红队**（顾问的专用姿态） | 在 G2 前专门做**反证检索**与结论攻击 | 构造反例、找相反数据、质疑口径 | 与出结论者为同一实例 |
| **专员** | 单个子问题的一站式负责人 | 在方向内自主决定检索/清洗/分析方法 | 触及 A 层范围、跨项目复用契约 |

**硬约束：**

- **实现与复核必须不同实例**：谁写的 claim，不能由谁做该 claim 的独立复核。
- **红队不得由结论作者兼任**；小项目可由经理兼任红队，但必须在 `03` 登记"红队 = 经理"。
- 顾问只说不做；经理尽量不亲自检索，把上下文留给判断。

## 2. 工单映射

调研沿用四件套，语义平移如下。**形式完全一致，不另造体系。**

| 内核概念 | 调研语义 | 落盘 |
|---|---|---|
| 工单 | **一次调研项目**（聚合工单）或**一个子问题**（子工单） | `workspace/p-*/` 或 `analysis/sub/<子问题>/` |
| `01-目标与设计` | 研究问题、范围、假设、方法、验收标准（**唯一 authority**） | 项目 `_dev/01-目标与设计.md` |
| `02-施工路线图` | 调研路线图：子问题拆解、阶段门、里程碑、关闭标准 | 项目 `_dev/02-调研路线图.md` |
| `03-开发状态` | 调研状态：阶段、来源/claim 计数、悬置问题、复核登记 | 项目 `_dev/03-调研状态.md` |
| `04-施工日志` | 调研日志：检索决策、推翻的结论、来源异常、口径变更 | 项目 `_dev/04-调研日志.md` |
| golden 数值 | **基准事实**（关键数字 + 口径 + as-of），冻结为断言 | `analysis/findings/facts.json` |
| 验收命令 | `sa lint` + 覆盖矩阵 + 引用校验 + 关键数字复算 | 见 §6 |
| 设计路线 | **子问题树**（需求层，不写技术细节） | 项目 `_dev/设计路线.md` |
| 挂起 / 归档 | 调研暂停 / 已交付结项 | `suspended/` `archive/` |

**聚合规则：** 调研项目的里程碑 = 子问题工单。聚合工单的 `03` 只写汇总与引用，**禁止双写**子工单状态。

## 3. 双层 `_dev`

| 层 | 管什么 | 不管什么 |
|---|---|---|
| 仓级 `_dev/` | 框架代码、规范、模板、数据源适配 | 任何具体调研内容 |
| 项目级 `_dev/` | 一次调研的范围、路线、状态、日志 | 框架能力缺口（后者升格为仓级工单） |

项目级 `_dev` 允许**轻量起步**：G0 只需 `01`；进入 G1 补 `02/03`；开始采集时补 `04`。

## 4. 决策分层（调研版）

| 层 | 内容 | 谁定 | 何时 |
|---|---|---|---|
| **A** | 研究问题、范围边界、交付形态与截止、对外口径、是否可公开 | **必须问用户** | G0，一次性问全 |
| **B** | 方法选型（定量/定性/案例）、源策略、证据门槛、子问题拆法 | 顾问给观点 → 经理拍板；拿不准升级问用户 | G0–G1 |
| **C** | 检索式、字段口径、清洗规则、命名、脚本实现 | 干事/专员自主 → 经理终审 | 施工期，不问用户 |

**典型误置：** 把"用哪个数据库查"（C）拿去问用户；把"这份报告能不能对外发"（A）自己拍板。

A 层问题在 G0 集中问完，施工期不打断用户。三个硬触发例外同内核：硬边界、范围级新问题、用户预先声明。

## 5. 阶段门

```text
G0 立项与范围 ──► G1 采集完成 ──► G2 分析收敛 ──► G3 交付
   建议/构建中        施工中           施工中          已达成
```

| 门 | 名称 | 关闭标准（逐条可检查） | 检查方式 |
|---|---|---|---|
| **G0** | 立项与范围 | ① 问题可回答且边界明确；② `brief/` 与 `_dev/01` 一致；③ 交付形态、验收标准、截止已定；④ A 层问题已全部答复 | 经理对照 `01` 逐条确认 |
| **G1** | 采集完成 | ① 覆盖矩阵每个子问题至少 1 个 E1/E2；② 关键数字有 primary source；③ 检索日志完整（可复现）；④ 缺口已显式登记 | `analysis/coverage.md` + `search/queries.jsonl` |
| **G2** | 分析收敛 | ① 全部 claim 有证据；② 反证轮已完成并留痕；③ 冲突已解释或标注未决；④ `sa lint` 零错误 | `sa lint` + 红队记录 |
| **G3** | 交付 | ① 报告引用校验通过；② 关键数字复算一致；③ 版本快照已打；④ 局限章节如实 | 交付前检查单（`04-工作流.md`） |

**阶段门是硬门**：不满足就留在当前阶段，不得"先写报告后面补证据"。

**唯一例外是显式 waiver**：确实只能条件性通过时，在 `project.json` 的 `gate_waivers` 登记 gate、理由、日期、批准人与范围，并把 `_dev/03` 对应门标为 🟡。waiver 不是降级——缺口、替代方案与影响仍须写入覆盖矩阵和报告局限；标 🟢 却留 waiver 会被 lint 视为不一致。

## 6. 验证级别（调研版）

| 级别 | 适用 | 复核义务 |
|---|---|---|
| **L0** | 对外发布、影响决策、争议议题 | 全部 claim 独立复核 + 关键数字**复算**（重跑取数或独立来源核对） |
| **L1**（默认） | 一般内部调研 | 抽查 ≥30% claim（必含全部高置信度结论）+ 关键数字复算 |
| **L2** | 小范围、低风险、纯信息整理 | `sa lint` + 经理终审；关键数字仍须抽 1–2 个复算 |

**复核 = 独立工作**：复核者按 claim id 逐条给出"通过 / 存疑 / 驳回"及理由，写入 `03` 的复核登记表。

## 7. 继承的纪律（点名，便于检索）

- **禁止双写**：`开发状态.md` 只做索引；项目 `03` 是项目状态的唯一真相。
- **先文档后实现**：结论先入 claim 台账，再进报告；口径先入口径卡，再进表格。
- **失效文档随手修**：经理在调研中撞见过时引用、错误口径、失效链接，当场修正。
- **交接制度**：跨会话的调研项目，在 `_dev/` 内写"研究交接"（当前判断、未决问题、下一步），不依赖上下文。
- **返修复用 session**：单点返修/复审复用原实例；跨阶段一律新上下文。
- **粒度**：一次立项 = 一个项目或一个子问题；子问题不拆成独立项目。

## 8. 研究的中立性（2026-10-20 立规，用户拍板）

**调研分析是决策支持，不是替客户决策。** 我们可以提出想法、方案、选项，但不能左右方向；材料必须让读者自己判断。

### 8.1 三层输出，不得混写

| 层 | 内容 | 允许的表达 |
|---|---|---|
| **事实层** | 来源、数据、口径、冲突 | "X 为 Y"（带来源与置信度） |
| **推论层** | 基于事实的判断、模型输出、假设 | "在假设 A 下，B 成立；若 A 不成立，则……" |
| **选项层** | 可选路径、方案、代价、条件 | "选项 1 需要……；选项 2 需要……"（对称呈现） |

**禁止**把选项层写成事实层的结论，也禁止在事实层夹带方向性判断。

### 8.2 禁用语与替代表达

| 禁止 | 替代 |
|---|---|
| "建议 / 推荐 / 应该 / 必须" | "若目标是 X，则 Y 更匹配；代价是……" |
| "优先做 / 不做 / Go / No-Go" | "在该权重与假设下，模型输出排序为……；排序随权重变化" |
| "我们的位置 / 我们的机会" | "能力匹配假设（需客户确认）" |
| "行业普遍认为" | "来源 A（等级）称……；来源 B 持相反口径" |

### 8.3 选项必须对称

每个选项至少给：成立条件、所需资源、时间、主要风险、证据强度、什么情况下不成立。**不得只给一个方案**；若客户只要一个，也须附"为什么不是另外几个"。

### 8.4 决策权归客户

- 可以提供决策矩阵、权重、评分，但**权重由客户确认**；我们只展示"权重变化会如何改变排序"。
- 不替客户设定目标函数；不把"商业上更优"当作唯一标准。
- 内部观点、倾向、商业方案放到 `analysis/notes/` 的内部文件，不进入对外研究材料。

### 8.5 图表与标题

- 图表标题描述"图展示了什么"，不写"应该做什么"。
- 例：不写"优先验证水稻纹枯病"，写"机会评分：六维模型输出"。
- 评分表的列名用"约束/条件"，不用"决策/可做"。

### 8.6 主观性审查（交付前必做）

- [ ] 每条结论能归入事实/推论/选项三层之一；
- [ ] 没有"建议/应该/优先/必须/推荐/不做"等方向性用语；
- [ ] 选项对称，附条件、代价与反证；
- [ ] 图表标题与列名中性；
- [ ] 权重与假设显式，且给出敏感性；
- [ ] 内部观点没有混入对外材料。

## 9. 与内核冲突时

本节原“其余以内核为准”的自动回落规则已由 2026-10-26 用户确定的新方向取代。现有项目按已落地的目录、状态、证据与版本契约维持兼容；新研究循环以[专业调研循环](../09-专业调研循环.md)收敛的业务设计为依据，未定事项显式登记，不从工程角色或生命周期推导新的业务约束。
