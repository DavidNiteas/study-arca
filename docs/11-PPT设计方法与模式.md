# 11 · PPT 设计方法与模式

中文 | [English](en/11-ppt-design.md)

本规范服务于研究内容的视觉表达；来源与中立性遵循 [03](03-证据与溯源.md)、[01](01-调研治理.md)，交付遵循 [07](07-交付与PPT.md)。默认原创画布，明确指定模板时兼容。模式是解决信息关系的方法，不是固定坐标、配色或空白成品。

## 1. 从要理解的问题开始

先确定受众、场景和阅读方式：会议投影需要当场看懂，独立阅读需要补足上下文。每页写一句“读者看完能理解什么”，再选择支撑它的证据。结论不足时表达问题、冲突或边界，不为写结论标题而制造结论。

辨认信息关系，再选择视觉表达：比较、组成、过程、层级、空间、机制、证据差异或条件选项。多种关系并存时确定主关系，细节可放备注、附页或查阅表，不把整段报告塞入图形。

在 [设计意图样例](../templates/ppt/design-intent.md) 中记录：核心表达、内容来源、关系、构图及理由、阅读顺序、表达边界和验证重点。可按页或同类页组记录，不要求机械填满每个字段，不新建第二份研究真相。

## 2. 按内容选择设计模式

| 模式 | 回答的问题 / 构图方法 | 不适用与常见误读 |
|---|---|---|
| 共同基准比较 | 谁多谁少？采用同基线条形或点图，直接标注单位、期间与分母 | 统计口径不同不能连成趋势或同榜排名；先做口径分组 |
| 组成与分解 | 什么构成整体？整体—部分展开，比例可信时才用面积编码 | 部分重叠、总量不明时不用百分比饼图；成员圆大小不自动表示份额 |
| 过程与分岔 | 如何发生、何处改变？沿路径布置阶段、条件与分支 | 不把仅相关的观察连成因果；反馈环须有依据 |
| 分类分支 / 图谱 | 类别如何组织？主轴、分支、代码、代表对象与交叉索引 | 空间距离不暗示计算相似度；层级不等于演化；环形也不能乱放连接 |
| 对象与作用位置 | 什么作用于哪里？画对象轮廓、相关部位、作用标记和说明 | 机制示意不冒充真实结合结构；抑制符号指向被抑制者，不颠倒催化关系 |
| 配比与组合 | 哪些成分、什么比例？成分节点、配比数字、汇合到试验条件与指标 | 圆面积不是效力；混用不证明协同；不同指标不作横向排名 |
| 证据对照 | 哪项观察支持哪种回答？按对象、层级、对照与局限组织，可配场景简图 | 田间防效不等于田间协同；来源等级不等于结论已独立验证 |
| 路径与条件 | 有哪些对称选项？同一起点分出路径，分别标条件、投入、回答与局限 | 顺序、颜色和尺寸不能偷偷替用户排优先级 |
| 精确查阅表 | 逐项核对什么？列名清楚、单位统一、关键列突出 | 不为反格子化而牺牲查阅效率；长段解释放表外 |

不要把表格全部换成圆圈。图形必须承担组织、比较或解释任务；若没有比表格更清楚，保留表格。同类过程可复用视觉语法，比如同一呼吸链上突出不同位点；跨页变化由内容驱动，不设“每几页换一次布局”的配额。

关键文献页按[研究分析与论证](13-研究分析与论证.md)呈现实验逻辑，而非年份与来源编号列表。一个分子可展开2–3页：机制框架、关键实验、跨研究综合；具体页数由解释需要决定。自绘流程注明依据论文重建，保留干预、对照、观察和判断；来源页脚给可识别的作者/年份/短题名。结构转为矢量时保留原高亮、图例与范围说明。

### 2.1 长篇研究 deck 的 session 骨架

长篇研究汇报需要同时支持现场讲述和事后浏览。当内容跨越多个研究阶段、方法族或工具模块时，可建立层级化 session 骨架：

```text
封面 → 目录 → 主 session → 子 session（需要时） → 内容页 → 进展/总结 → 结束页
```

- 主 session 表达一个完整研究段落，子 session 只切开过长的同层内容；不为每几页机械建立分节。
- 主分节页承担导航和范围宣告，子分节页的视觉层级应低于主分节页；内容页继续承担证据。
- 目录同时显示主 session、必要的子 session 和实际页码；页码应来自当前页面结构，不手工维护。
- 进展总结与结束致谢是不同页面角色。结束页只负责收束演示，不在最后一页重新引入未处理的研究主张。
- 目录、分节和子分节均不是内容证据；其文字只描述结构，不替页面生成结论。

### 2.2 页面文字的角色分工

同一页上的文字应按任务分工，而不是套用固定“标题—副标题—正文”模板：

- **标题**：命名研究对象、组件、判断或清晰问题。避免口号化、账本式过程语和无法对应内容的抽象词。
- **页面主张**：用一句话说明本页希望读者形成的理解。它必须能独立成立，并与标题构成主从关系；示意图、原始结果图、软件截图等以对象本身为主要阅读入口的页面，可以不设主张句。
- **证据标签**：只用于对象、关系、单位、状态和来源。不要把“示意、非实测、示例结果”等审计或制作过程标签当作科学免责声明。
- **收口句**：仅在页面需要压缩判断、形成转折或引出下一层分析时使用；不能重复标题或塞入新的未展开论证。
- **导航文字**：页码、章节名和页脚只帮助定位，不承担研究结论。

若一段文字既不是对象命名、页面主张、证据说明，也不是导航，应重新判断它是否有必要出现在页面上。

### 2.3 路线、架构与业务流的分工

- **技术路线**回答“研究如何展开、不同方法如何汇合”。
- **系统架构**回答“组件如何分层、职责与依赖如何组织”。
- **业务流**回答“输入经过哪些处理、在何处产生什么输出”。
- **状态机**回答“对象如何迁移、哪些状态可恢复或终止”。

这些图可以共享节点和颜色语法，但不能用同一张图同时承担全部问题。信息角色不清时，先拆页或明确主关系，再选择图形。

## 3. 从构图到布局 LR

- 建立视觉中心与阅读顺序：标题、主体对象、关键关系、证据/边界、来源。先画主对象和关系，再摆标签，不先铺满等大卡片。
- 留白用于分组；尺寸与颜色表达主次。文本保持可读，删减或拆页通常比持续缩小字号更有效；字号按实际投影/阅读预览判断，不规定万能字号。
- 连线有起终点，交叉可辨。箭头、抑制线、普通关联线分开使用；标签靠近对应对象。线段不会因为好看就获得科学含义。
- 真实结构、统计图、机制示意分别标明身份。科学结构由可信来源或领域工具生成；自由绘图不能补造残基、距离或结合证据。
- 布局 LR 使用稳定元素 ID 与内容引用，记录层次、坐标、文字、路径和素材。具体语法取决于适配器；当前实验格式不是跨媒介通用标准。
- 全篇同时看：开场定范围、主体展开证据、结尾呈现限制与讨论入口。检查重复是否帮助对照，或只是复制了默认布局。

### 3.1 对齐优先，容器后置

先用画布边界、基线、列和间距组织内容，再判断是否需要边框、卡片或底色。若对齐关系已经足以表达分组，额外容器往往只会增加噪声。

- 同高区域应对齐顶边和底边；上层分栏与底部横条应对齐总宽。
- 同一纵向结构中的标题、对象和图示应在共享内容边界内组织，不因个别元素过长而破坏整体轴。
- 分组容器只在成员关系必须被显式识别、背景需要隔离证据层级或内容会被移动复用时有价值。
- 不用边框和底色弥补错位；先修正位置、尺寸和间距。

### 3.2 用空间强化主对象

空白不是必须填满，也不是可以忽略。判断空白的任务是承托主对象、分隔关系，还是暴露了版面失衡。

- 主体偏小、关系线过短或下半区失衡时，优先放大核心节点、结构、图或关键句，并同步延长连接线。
- 次要区域拥挤时，优先删减、拆页或移动信息；持续缩小字号会同时损失可读性和信息层级。
- 大结论句需要足够的视觉权重时，可占据整行或整栏；不要让它退化成页脚注。
- 图片保持原始宽高比。单张证据图足以说明问题时，一图一页比加入装饰性说明更清楚。
- 不用无关图形、纹理或半透明色块填满剩余空间。

## 4. 视觉反馈如何改变设计

执行：内容与来源 → 设计意图 → 布局 LR → 目标软件实际渲染 → 读图 → 修改 → 重渲染与复看。先确认工具可渲染且模型真的可读取图片；失败记 pending，不以导出成功替代看图。

评审分四个问题：

1. **理解**：第一眼看见什么？不读长正文能否辨认主关系？
2. **准确**：箭头、面积、位置、类别和数值是否表达了来源不支持的含义？
3. **可读**：标签遮挡、孤立标点、密度、对比度与字体是否影响理解？
4. **全篇节奏**：哪些重复便于比较，哪些重复掩盖了信息差异？

机器边界检查只覆盖其中一部分。用页码/元素 ID 记录问题、理由和改动；源数据问题回到分析，设计选择问题改意图，坐标问题改布局。没有新增问题时结束循环，不为凑次数重画。

### 4.1 返修前先判断问题归属

- **内容/来源问题**：数字、结论、范围或引用不成立——回到分析，不在版面层修补。
- **语义编码问题**：颜色、线型、箭头、面积或空间位置暗示了错误关系——回到设计意图。
- **布局问题**：遮挡、错位、比例失衡、空白利用不足——修改布局 LR。
- **渲染问题**：字体替换、编码错误、主题阴影或宿主软件差异——修正渲染器或环境适配。
- **发布问题**：页码、目录、外部引用、文件哈希或 release 副本不一致——在输出和发布流程中修复。

问题归属错误会导致“看起来改了，实际根因仍在”。只改变换行、字号或颜色，不能修复错误的证据关系。

### 4.2 发布前检查补充

实际读图之后，发布前还应确认：

- 目录、章节号、页码和交叉引用与最终页序一致；能由结构生成的不要手工重复维护。
- 标题和主张未遮挡章节标记、页码或其他文字；关键信息不依赖演示者口头补偿。
- 原始图表、截图和真实结构保持比例，来源可追溯，未加入未经支持的数字或结论。
- 同类状态、关系与完成度使用一致刻度；若刻度为项目选择，应明确其边界，不自动上升为通用规范。
- PPTX 无外部资源依赖；发布目录与冻结副本哈希一致。

通过时绑定最终输出与预览哈希，明确 self/independent；自查通过不意味着用户已验收，也不意味着科学事实获得独立复核。按 [09](09-专业调研循环.md) capture 设计意图与审查记录，作为 outcome/answer 的 materials；presentation 仍引用内容、布局、输出、预览四项，无需扩展现有 schema。

## 5. 持续沉淀

项目内先记实际观察：问题是什么、原设计为何失效、如何修正、读图结果、证据位置、未解决事项。使用 [案例记录](../templates/ppt/design-case.md)。用户反馈、自查、独立复核分别记录，满意度不替代研究证据。

能迁移的经验进入 [案例索引](presentation/README.md)：移除业务敏感内容，保存必要的设计关系和反例；根仓不得复制 workspace 成品。单个成功样例标为“已观察案例”，多场景复验后才有依据扩大适用范围；仍可直接作为有边界的参考，不设人为次数门槛。

案例进入产品仓前必须去项目化：移除项目名、客户/研究对象、内部版本号与页数统计、本地路径、人员信息、截图和可识别交付物；只保留问题、关系、判断与验证边界。发布前同时检查当前树和历史对象，确认敏感内容尚未进入远端；如在本地历史中发现泄露，应先停止推送，再按 [07](07-交付与PPT.md) 的 Git 历史维护流程完成清理和复核。

常规代理可记录项目经验；跨项目规范/技能变更归框架工单。修改模式时说明新增证据、适用边界、冲突与取代关系，保留历史；不要每完成一页就增加一条普遍硬规则。案例不产生新的审批流程，也不自动授权公开发布项目资料。
