# 16 · 复盘、对齐与适配输出（sa.synthesis/1）

> 本文定义总结/复盘型工作区的业务流程。它回答“如何先让自己真正理解当前工作，再面向不同对象组织报告”，不改变 [09](09-专业调研循环.md) 的外部问题研究循环。
>
> 状态：第一层已落地：追加式复盘/对齐记录、修正记录、Work Snapshot 和快照绑定渲染可用；完整阶段门、输出登记联动和真实材料端到端验收仍待完成。

## 1. 业务定位

报告不是流程起点，而是认知完成后的表达结果。面向他人汇报、讲解或交流之前，用户与代理团队必须先对当前工作形成可追溯、可复核、可继续演进的共同理解。

总结型工作区采用四个业务阶段，并在循环与输出之间设置快照门：

```text
原始材料
  → 复盘：形成结构化工作态
  → 对齐：确认事实、解释、缺口与下一步
  → 复盘-对齐循环：持续修正确认后的共同理解
  → 冻结中间产物
  → 适配输出：按受众、目的和媒介释放信息
```

这与研究型工作区的差别是主对象不同，而不是是否允许调研：

| 工作区 | 主对象 | 主循环 | 调研的位置 |
|---|---|---|---|
| `research` | 外部问题、来源与证据 | 立项、调研、分析、讨论、呈现 | 主过程 |
| `synthesis` | 用户正在进行的工作 | 复盘、对齐、循环、快照、适配输出 | 辅助子过程 |

Synthesis 中的背景调研、竞品比对、工作缺口核查等仍可按 [09](09-专业调研循环.md) 执行，但其产物必须先成为当前 synthesis 工作区可追溯的材料，不能改变工作区身份，也不能替代用户对自己工作的第一人称记录。

## 2. 不变量

1. **身份来自元信息**：`project.json.workspace_type` 决定 research 或 synthesis，目录名和所在位置不决定身份。
2. **事实归属不变**：工单、状态、材料、结论和快照属于当前工作区；跨工作区内容进入当前工作区时必须物化为不可变副本。
3. **用户提供优先但不越级**：用户对自身工作、目标、决定和状态的陈述具有高处理优先级；用户转述的外部事实仍按材料来源与核验状态判断。
4. **理解先于表达**：复盘和对齐未完成时，可以生成内部草稿，但不得把排版成品当作“已经理解工作”。
5. **输出消费冻结版本**：正式输出绑定不可变的工作快照，不直接读取持续变化的 `work-model/model.json`。
6. **未知项是正式内容**：缺少材料、状态不清、因果未证实和计划未确定都必须保留为未知或待确认，不得用语言润色填空。
7. **打包是独立用户动作**：生成、交付和发布都不自动触发压缩；仅当用户明确要求时，包进入 `publish/packed/`。

### 2.1 管家式协作契约

Synthesis 首先是一种协作关系，其次才是一组文件。代理更像用户的“项目管家”：帮助记住、整理、发现关系和提醒缺漏，但不替用户经历、判断或决定。

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户（主理人） | 提供亲身经历、目标、判断、偏好、决定和资料访问授权；确认或修正代理理解 | 不需要按表格预填所有字段 |
| 代理（项目管家） | 接住原始口述、复述理解、整理关系、发现高影响缺口、温和引导、检索并归档资料、维护版本 | 不虚构经历、不替用户拍板、不把未提及当成未发生 |

协作遵循四个原则：

1. **引导而非审问**：先展示当前理解，再围绕影响最大的缺口提问；不按清单逐项逼问。
2. **补记而非代写**：代理可以归并、比较和提出推断，但必须保留用户原话并标明推断依据。
3. **提醒而非裁定**：代理能指出“这里可能漏了一项内容”或“这两件事可能存在依赖”，不能自行认定用户遗忘、遗漏或做错。
4. **保留选择权**：用户可以直接回答“不知道”“没发生”“暂时不重要”“不想说”或“以后再说”，这些回答都应被正式记录。

每次自然语言输入建议经过以下循环：

```text
接住原始口述
  → 复述当前理解
  → 结构化到工作模型
  → 检查内容关系与缺口
  → 用少量问题温和补缺
  → 接收文件、目录或来源路径
  → 给出本轮记录回执
  → 用户确认或修正
```

不是每一轮都必须走完整步骤；这个循环用于保证代理不会从“听到一些话”直接跳到“生成一份报告”。

#### 原始口述

用户最初通常使用自然语言口述。代理应优先记录其原意，再做结构化：

- 保留本次口述的原始文本或用户确认过的准确摘录；
- 原文作为 `user_statement` 来源，不直接改写为材料事实或代理结论；
- 结构化模型中的复述和归并标明为代理理解，允许用户修正；
- 聊天上下文本身不是长期事实源，需要长期保留的内容必须落盘并登记。

#### 引导式补缺

代理维护一份“缺口池”，但不应把缺口池变成审问清单。提问按影响排序：

| 优先级 | 判断 | 处理 |
|---|---|---|
| 立即询问 | 答案会改变当前理解、结论、风险、资源或披露边界 | 本轮集中问 1–3 个 |
| 下轮询问 | 影响结构完整性，但不阻止当前理解继续推进 | 放入下一轮议程 |
| 暂不询问 | 只影响细节完整度或当前用途无关 | 保留为未知或待补资料 |

每次提问应让用户知道“为什么问”，并尽量给出可辨识的上下文。例如：

> 我目前理解这项工作是“方案已经完成，但还没有经过完整业务验证”。它和前面的迁移工作可能有关，不过这次没有提到验证结果。这里是验证尚未开始、结果没放进来，还是目前不需要验证？如果暂时不确定，我先标为待确认。

好的引导具备以下特征：

- 先复述理解，再提出问题；
- 一次只聚焦一个主题组，通常不超过 1–3 个问题；
- 问题说明潜在影响，并允许用户直接否定代理的理解；
- 不连续追问用户已经表示不知道或不愿回答的内容；
- 不把清单完整度当成对人的考核；
- 不把用户的情绪、犹豫或口语化表达当成低质量材料。

#### 关系与缺口发现

代理进行的是有依据的提醒，可以从以下关系中寻找缺口：

- 目标出现，但没有对应行动、结果或结束条件；
- 出现成果，但没有验收、反馈、影响或材料依据；
- 多个事项存在先后关系，但依赖是否成立尚不清楚；
- 已计划事项缺少负责人、时间、前置条件或范围；
- 同一事项出现状态冲突或不同版本；
- 用户反复提到某对象，但它尚未成为明确工作主题；
- 当前工作可能与另一个工作区有关，但还没有物化引用；
- 报告受众或敏感边界会改变信息能否释放。

代理在提醒时使用“尚未看到”“可能需要确认”“我推测存在关联”，不使用“你一定忘了”“显然没有做”等判决式表达。

#### 资料投递与路径接管

用户可以用两种方式提供材料：

1. 将文件或目录放进当前工作区的 `brief/inbox/`；
2. 直接告诉代理本地路径、共享盘路径或其他可访问来源。

`brief/inbox/` 只是本地暂存区，不是事实权威，也不进入 Git。代理接收资料时执行：

1. 先盘点文件名、类型、大小和范围，不擅自扫描相邻目录；
2. 与用户确认哪些内容与当前工作有关；
3. 优先通过 `sa input add` 复制到 `brief/provided/u-NNNN/` 并登记角色、权威、核验状态和哈希；
4. 原件和用户目录不修改；需要长期保留的内容以工作区内副本为准；
5. 导入完成后给出数量、失败项、跳过项和归档位置回执。

代理只访问用户明确给出的路径及其必要子范围。遇到无权限、格式不支持或材料过大时，应说明原因并请求新的路径、导出文件或更小范围，不得绕过限制。

#### 每轮回执

每轮交互结束前，代理应给出简短回执：

- **已记录**：本轮新增或修正了什么；
- **当前理解**：现在把工作理解成哪几条主线；
- **仍不确定**：哪些内容需要用户确认或补充；
- **待补资料**：需要哪些文件、目录或外部来源；
- **下一步**：代理接下来准备整理、检索或询问什么。

回执服务于用户纠错，不应复制整份工作模型。用户确认后，代理再更新稳定的工作版本；未确认内容继续保留为代理理解或待确认项。

## 3. 四个业务阶段

### 3.1 复盘：原始材料到结构化工作态

复盘不是逐段摘要，而是把分散信息整理成能够支撑理解、追问和后续表达的完整工作态。

输入至少包括：

- `brief/brief.md`：工作对象、用途、已知范围和用户原话；
- `brief/provided/manifest.json`：用户提供材料的角色、权威和核验状态；
- `references/index.json`：跨工作区物化引用；
- `work-orders/`：当前工作区负责的工单；
- 必要的辅助研究材料。

复盘需要形成以下工作维度，实际字段由 `sa.work-model/1` 承载：

| 维度 | 至少要回答的问题 |
|---|---|
| 主题 | 正在推进什么，为什么做，边界是什么？ |
| 状态 | 已完成、进行中、阻塞、待启动还是已取消？ |
| 进展 | 在什么时间发生了什么，当前推进到哪一步？ |
| 结果 | 有哪些可观察产出、指标、反馈或影响？ |
| 阻塞与依赖 | 卡在哪里，依赖谁或什么条件？ |
| 下一步 | 用户已经计划什么，哪些只是候选或代理推断？ |
| 关系 | 人物、团队、上下游和跨工作区依赖是什么？ |
| 未知 | 哪些关键事实、口径、时间或因果关系仍缺失？ |

每个内容项必须标明来源层：

- `user_statement`：用户原话或用户对自身工作的明确陈述；
- `material`：用户提供材料或物化引用中的可见记录；
- `inference`：代理对多个材料的归并、比较或推断；
- `unknown`：当前材料未覆盖、存在冲突或尚待确认。

复盘“完整”不等于掌握所有事实，而是相对于声明的范围与验收目标：

- 关键工作主题没有漏项；
- 每个主题的状态、进展、结果、阻塞和计划口径清楚；
- 每个事实能找到材料或用户陈述；
- 关键冲突和缺口已经显式登记；
- 对外部事实的核验要求没有被“用户提供”自动豁免。

复盘产出是可继续修改的工作态，不是最终报告。当前对应文件为 `work-model/model.json`。

### 3.2 对齐：结构化材料到共同理解

对齐的目标是让用户与代理团队对同一版结构化材料形成可核对的共同理解。代理团队内部也要先完成这一过程，不能把几个代理各自的推断直接拼成报告。

对齐不是重复复述，而是处理五类认知差异：

| 类型 | 含义 | 处置 |
|---|---|---|
| 已确认 | 用户与代理对含义、状态和范围一致 | 固定在当前工作版本 |
| 有争议 | 用户陈述与材料冲突，或双方解释不同 | 保留双方版本，进入定向核查或用户确认 |
| 代理推断 | 由多个事实归并出的解释 | 标明推理依据、边界与失效条件 |
| 缺口 | 缺少会改变理解或结论的关键信息 | 优先向用户集中提问；不重要的缺口保留为未知 |
| 决策点 | 下一步需要用户选择的方向或取舍 | 给出选项、依据、风险和未知，不代替用户拍板 |

对齐阶段至少回答：

1. 我们现在知道什么，分别来自哪里？
2. 我们还缺什么，其中哪些会改变当前判断？
3. 有哪些可成立但尚未证实的推断？
4. 下一步有哪些可能，各自依赖什么条件？
5. 哪些内容属于用户决定，不能由代理替选？

高影响问题应集中一次询问。低影响缺口可以保留为未知，不用长问卷换取表面完整。

### 3.3 复盘-对齐循环

每次循环是一个有边界、可复盘的认知版本：

```text
选择本轮目标
  → 复盘新增材料与现有工作态
  → 标出冲突、缺口和推断
  → 与用户做一次集中对齐
  → 确认共同理解、未决项和下一步
  → 判断是否达到本轮关闭条件
```

每轮至少记录：

- 轮次 ID、日期与目标；
- 消费的材料 ID 和版本；
- 工作态发生了哪些变化；
- 哪些认知已对齐，哪些仍有争议；
- 产生了哪些新问题或辅助研究任务；
- 关闭理由与限制；
- 下一轮入口或明确终止条件。

循环可以因“信息足够支持当前用途”而关闭，也可以因时间、材料获取或用户决定而关闭。关闭必须如实记录原因，不能把“找不到”写成“并不存在”。

新增材料不会自动覆盖旧轮次。需要改变已确认内容时，建立新的工作版本；正式输出需要重新绑定新快照。

复盘-对齐循环通过 `synthesis/ledger.json` 追加记录，不允许改写历史。当前记录类型如下：

| type | 作用 | 必要内容 |
|---|---|---|
| `round` | 开启一轮复盘-对齐 | `topic`、`topic_title`、`related_work_items`、`goal`；子主题另带 `parent_topic`、`parent_snapshot` |
| `review` | 记录代理本轮整理与模型变化 | `round`、`summary`、`changes`、`gaps`、`materials` |
| `question` | 记录高影响问题 | `round`、`text`、`priority`、`why` |
| `answer` | 记录用户回答、未知、跳过或暂缓 | `round`、`question`、`status`、`summary` |
| `correction` | 记录用户修正及其目标 | `round`、`target`、`summary` |
| `alignment` | 关闭一轮对齐 | `round`、`summary`、`narrative`、`items`、`next_steps` |
| `snapshot` | 冻结已对齐的工作模型 | `round`、`label`、`path`、`sha256` |
| `decision` | 用户决定本轮之后的循环方向 | `round`、`actor: user`、`decision`、`rationale`、`materials` |

`review`、`correction` 和 `alignment` 自动记录写入时的 `model_sha256`。关闭轮次前，本轮提出的所有问题都必须有回答、未知、跳过或暂缓结论。

`alignment.items` 用于保存可复用的结构化判断。每项包含 `statement` 和 `status`；`status` 只允许 `confirmed`、`disputed`、`unknown`、`deferred`、`out_of_scope`，并可关联材料和工作主题。

对齐完成后，用户选择以下循环出口之一：

| decision | 含义 | 附加要求 |
|---|---|---|
| `exit` | 当前主题达到本轮目标，跳出 | 无 |
| `continue` | 同一主题继续下一轮 | 下一轮引用本轮快照 |
| `drill_down` | 展开某个下层主题 | 指定 `target_topic` 和 `target_title`；子轮次引用父主题与本轮快照 |
| `park` | 暂挂，不继续也不闭合整个项目 | 指定 `resume_when` |

一个主题可以通过多轮继续深化。只有父轮次完成用户决定后，才能创建对应的续轮或子主题轮次。

下钻前，秘书可以给出一组候选项供用户比较，而不必把问题压缩成“是否下钻”。候选项应说明：建议的 `topic` 与标题、它展开父叙事中的哪一段、准备回答的核心问题、现有材料入口、已知缺口，以及推荐的讨论顺序。这组候选项只是导航建议，不写入事实台账，也不预先创建轮次；只有用户选定 `drill_down` 目标后，才能登记决定并建立子轮次。

```powershell
python scripts/sa.py synthesis status <project>
python scripts/sa.py synthesis apply <project> --file <records.json>
python scripts/sa.py synthesis snapshot <project> --round r-0001 --id snap-0001 --label "第一轮对齐"
python scripts/sa.py synthesis alignment <project> --round r-0001
python scripts/sa.py synthesis decision <project> --round r-0001 --id d-0001 --decision drill_down --rationale "展开方法体系" --target-topic method-paradigm --target-title "方法范式" --material u-0001
python scripts/sa.py synthesis build <project> --snapshot snap-0001 [--docx]
```

可使用 [复盘记录示例](../templates/synthesis/records.example.json) 组织输入；示例不是项目事实，材料 ID 和工作主题 ID 必须由当前工作区实际提供。

### 3.4 冻结中间产物

一轮复盘-对齐关闭后，应冻结一份工作快照。快照至少固定：

- 工作模型内容与内容层；
- `as_of`、覆盖期间和范围；
- 材料 ID、物化引用 ID 与哈希；
- 用户确认、代理推断、未知项和争议项；
- 对齐问题和处置结果；
- 允许的用途、受众边界与敏感限制；
- 生成快照所依据的工作版本。

快照是正式输出的唯一内容源。`report/` 中的 Markdown、`document.json`、HTML、DOCX 和 PPT 都属于可再生成的呈现层。

快照保存在 `synthesis/snapshots/<snapshot-id>/snapshot.json`。快照嵌入当时的工作模型、模型哈希、材料清单哈希、轮次和 `as_of`；同一轮对齐后如果工作模型继续变化，必须开启新轮次重新对齐才能冻结新快照。

### 3.5 适配输出：中间产物到报告

适配输出先决定“释放什么”，再决定“如何表达”。输出请求至少明确：

| 维度 | 要回答的问题 |
|---|---|
| 受众 | 本人、上级、团队、客户、合作方还是公开读者？ |
| 目的 | 自查、复盘、汇报、争取决策、交接还是说明？ |
| 渠道 | 阅读文档、现场讲解、邮件、网页还是演示？ |
| 时间 | 使用哪个 `as_of` 与覆盖期间？ |
| 范围 | 哪些主题纳入，哪些明确排除？ |
| 敏感边界 | 哪些内容不可披露，是否需要脱敏版本？ |
| 形式 | Markdown、DOCX、HTML、PPT 或其他格式？ |
| 长度与深度 | 一页摘要、完整报告还是分层附录？ |

输出遵循：

```text
Work Snapshot
  → Output Request（受众、目的、范围和敏感边界）
  → DocumentPlan / ExperiencePlan / DeckPlan
  → 格式渲染
  → 实际预览与视觉检查
  → outputs/registry.json 登记
  → 用户要求时进入 publish/packed/
```

不同受众可以改变选材、顺序、详略、语气和表达形式，不能改变同一快照中的事实层、未知项和置信边界。HTML、DOCX 和 PPT 共享同一内容依据；PPT 不能为了版面删除改变理解的关键对照或限制。

涉及外部发布或组织内正式汇报时，受众、敏感边界和可披露范围属于需要用户确认的范围决策。代理可以整理选项和风险，不得擅自扩大披露范围。

## 4. 阶段门

### G1 复盘完成

- 工作主题、目标、状态、进展、结果、阻塞、依赖和下一步在声明范围内可知；
- 每条实质内容有来源层，用户陈述与代理推断没有混写；
- 冲突、缺口与敏感限制已登记；
- 结构化材料可供用户阅读和纠错。

### G2 对齐完成

- 用户与代理对术语、状态、范围和关键因果解释形成一致或明确分歧；
- 高影响缺口已集中询问；
- 代理推断说明了依据和边界；
- 未由用户拍板的决策没有伪装成用户意见；
- 下一步候选与关闭条件清楚。

### G3 快照可用

- 快照绑定工作版本、材料哈希和 `as-of`；
- 快照可离线读取和独立审阅；
- 快照中的事实、推断、未知和争议层完整；
- 新工作态不会静默改写旧快照。

### G4 输出可释放

- 输出请求写明受众、目的、渠道、范围、敏感边界和格式；
- 正式输出绑定快照，而非未冻结模型；
- 每种格式的事实与边界一致；
- HTML/PPT 等视觉成品实际读取预览后登记审查；
- 打包仍然需要用户明确要求。

## 5. 目录与记录映射

| 当前路径 | 职责 | 本设计中的位置 |
|---|---|---|
| `project.json` | 工作区身份与生命周期 | 决定 research/synthesis |
| `brief/inbox/` | 用户投递的未登记材料暂存区 | 只作接收入口，不提供事实权威 |
| `brief/provided/` | 用户原始材料与哈希 | 复盘输入 |
| `work-orders/` | 当前工作区拥有的工单 | 工作对象与范围来源 |
| `references/` | 跨工作区物化副本 | 复盘输入 |
| `work-model/model.json` | 当前可编辑工作态 | 复盘与对齐的工作版本 |
| `synthesis/ledger.json` | 追加式复盘-对齐事件 | 轮次、问题、回答、修正、对齐和快照历史真相 |
| `synthesis/alignments/<round>.md` | 从 ledger 生成的对齐记录 | 人读、可复用的对齐产物；不反向成为事实源 |
| `synthesis/snapshots/<id>/snapshot.json` | 一轮认知的冻结产物 | `sa.work-snapshot/1`，正式输出的内容源 |
| `report/` | Markdown、结构化文档与渲染工作区 | 适配输出 |
| `outputs/registry.json` | 输出、请求、计划和审查登记 | 交付审计 |
| `deliverables/` | 已出稿冻结版本 | 正式交付快照 |
| `publish/packed/` | 用户显式要求后的压缩包 | 发布出口 |

Program 仍只维护下层 workspace/program 的引用与版本 pin，不保存工作模型、对齐结论、报告或快照。

## 6. 各受众的适配原则

| 受众 | 首要目标 | 典型结构 | 必须保留 |
|---|---|---|---|
| 本人自查 | 理解全局并发现缺口 | 工作主题全景、状态、冲突、未知、下一步 | 完整来源层和未决项 |
| 上级汇报 | 快速判断状态与需要支持的事项 | 结论先行、关键结果、风险、决策请求 | 口径、范围、关键限制 |
| 团队协作 | 形成共同上下文并明确分工 | 目标、现状、依赖、责任、下一步 | 争议和未决责任边界 |
| 交接接手 | 让他人无需聊天历史也能继续 | 目标、状态、资料入口、决策链、开放问题 | 材料、快照、未完成事项 |
| 外部交流 | 在授权范围内形成可信说明 | 背景、成果、边界、后续 | 敏感边界、事实与推断分离 |

格式适配不能把“内部自查需要的完整性”直接暴露给所有受众。删减是信息释放决策；保留限制和未知项是事实完整性要求。

## 7. 当前实现边界

已具备：

- `sa.workspace/1` 的 research/synthesis 身份；
- 用户材料登记与哈希校验；
- `sa.work-model/1` 的四层内容模型；
- 新项目模板中的 `brief/inbox/` 暂存区与忽略规则；
- `sa.synthesis/1` 追加式轮次、复盘、问题、回答、修正和对齐记录；
- `sa.work-snapshot/1` 冻结快照和指定快照渲染；
- `sa synthesis init|validate|status|apply|snapshot|alignment|build` CLI；
- 本地工单、跨工作区引用物化、输出登记与显式打包边界。

尚未完成：

- 更细粒度的阶段门和回执自动检查；
- 与 `outputs/registry.json` 的 synthesis 输出登记联动；
- 输出请求中的选材、脱敏和受众边界机器检查；
- synthesis 到统一 PPT/Deck 流程的完整适配；
- 用户真实材料上的端到端验收。

因此，当前实现已经能记录复盘-对齐循环并绑定冻结快照，但不带 `--snapshot` 的 `sa synthesis build` 仍是兼容性的工作态草稿。正式交付应使用 `--snapshot`，且不得以机制测试结果替代用户复核。

## 8. 最小验收

1. 用户只通过自然语言提供零散信息时，也能在不被审问式追问的情况下形成带来源层的工作主题、状态和未知项。
2. 每条实质内容可追溯；代理归并不会冒充用户原话。
3. 高影响缺口集中询问一次，未提供的信息保持未知。
4. 用户能够指出并修正工作态，修正产生新的循环记录而不是覆盖历史。
5. 正式输出绑定冻结快照，并写明 `as-of`、覆盖期间、受众与范围。
6. 更换 HTML、DOCX 或 PPT 不改变快照中的事实、未知和限制。
7. 跨工作区引用在本地可读且哈希可校验；权威仍指向原工作区。
8. 未获用户明确要求时不生成压缩包。
9. `brief/inbox/` 中的材料在登记前不进入分析和工作模型，登记后原文与哈希与工作区副本一致。
