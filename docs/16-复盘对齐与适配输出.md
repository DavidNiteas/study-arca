# 16 · 复盘、对齐与适配输出（sa.synthesis/1）

> 本文定义总结/复盘型工作区的业务流程。它回答“如何先让自己真正理解当前工作，再面向不同对象组织报告”，不改变 [09](09-专业调研循环.md) 的外部问题研究循环。
>
> 状态：业务层已确认；循环事件、Work Snapshot、机器校验和真实材料端到端验收仍待施工。

## 1. 业务定位

报告不是流程起点，而是认知完成后的表达结果。面向他人汇报、讲解或交流之前，用户与代理团队必须先对当前工作形成可追溯、可复核、可继续演进的共同理解。

总结型工作区采用四个业务阶段，并在循环与输出之间设置快照门：

```text
原始材料
  → 复盘：形成结构化工作态
  → 对齐：确认事实、解释、缺口与下一步
  → 复盘-对齐循环：持续修正确认后的共同理解
  → 冻结中间产物
  → 适配输出：按受众、目的和媒介释放信息
```

这与研究型工作区的差别是主对象不同，而不是是否允许调研：

| 工作区 | 主对象 | 主循环 | 调研的位置 |
|---|---|---|---|
| `research` | 外部问题、来源与证据 | 立项、调研、分析、讨论、呈现 | 主过程 |
| `synthesis` | 用户正在进行的工作 | 复盘、对齐、循环、快照、适配输出 | 辅助子过程 |

Synthesis 中的背景调研、竞品比对、工作缺口核查等仍可按 [09](09-专业调研循环.md) 执行，但其产物必须先成为当前 synthesis 工作区可追溯的材料，不能改变工作区身份，也不能替代用户对自己工作的第一人称记录。

## 2. 不变量

1. **身份来自元信息**：`project.json.workspace_type` 决定 research 或 synthesis，目录名和所在位置不决定身份。
2. **事实归属不变**：工单、状态、材料、结论和快照属于当前工作区；跨工作区内容进入当前工作区时必须物化为不可变副本。
3. **用户提供优先但不越级**：用户对自身工作、目标、决定和状态的陈述具有高处理优先级；用户转述的外部事实仍按材料来源与核验状态判断。
4. **理解先于表达**：复盘和对齐未完成时，可以生成内部草稿，但不得把排版成品当作“已经理解工作”。
5. **输出消费冻结版本**：正式输出绑定不可变的工作快照，不直接读取持续变化的 `work-model/model.json`。
6. **未知项是正式内容**：缺少材料、状态不清、因果未证实和计划未确定都必须保留为未知或待确认，不得用语言润色填空。
7. **打包是独立用户动作**：生成、交付和发布都不自动触发压缩；仅当用户明确要求时，包进入 `publish/packed/`。

## 3. 四个业务阶段

### 3.1 复盘：原始材料到结构化工作态

复盘不是逐段摘要，而是把分散信息整理成能够支撑理解、追问和后续表达的完整工作态。

输入至少包括：

- `brief/brief.md`：工作对象、用途、已知范围和用户原话；
- `brief/provided/manifest.json`：用户提供材料的角色、权威和核验状态；
- `references/index.json`：跨工作区物化引用；
- `work-orders/`：当前工作区负责的工单；
- 必要的辅助研究材料。

复盘需要形成以下工作维度，实际字段由 `sa.work-model/1` 承载：

| 维度 | 至少要回答的问题 |
|---|---|
| 主题 | 正在推进什么，为什么做，边界是什么？ |
| 状态 | 已完成、进行中、阻塞、待启动还是已取消？ |
| 进展 | 在什么时间发生了什么，当前推进到哪一步？ |
| 结果 | 有哪些可观察产出、指标、反馈或影响？ |
| 阻塞与依赖 | 卡在哪里，依赖谁或什么条件？ |
| 下一步 | 用户已经计划什么，哪些只是候选或代理推断？ |
| 关系 | 人物、团队、上下游和跨工作区依赖是什么？ |
| 未知 | 哪些关键事实、口径、时间或因果关系仍缺失？ |

每个内容项必须标明来源层：

- `user_statement`：用户原话或用户对自身工作的明确陈述；
- `material`：用户提供材料或物化引用中的可见记录；
- `inference`：代理对多个材料的归并、比较或推断；
- `unknown`：当前材料未覆盖、存在冲突或尚待确认。

复盘“完整”不等于掌握所有事实，而是相对于声明的范围与验收目标：

- 关键工作主题没有漏项；
- 每个主题的状态、进展、结果、阻塞和计划口径清楚；
- 每个事实能找到材料或用户陈述；
- 关键冲突和缺口已经显式登记；
- 对外部事实的核验要求没有被“用户提供”自动豁免。

复盘产出是可继续修改的工作态，不是最终报告。当前对应文件为 `work-model/model.json`。

### 3.2 对齐：结构化材料到共同理解

对齐的目标是让用户与代理团队对同一版结构化材料形成可核对的共同理解。代理团队内部也要先完成这一过程，不能把几个代理各自的推断直接拼成报告。

对齐不是重复复述，而是处理五类认知差异：

| 类型 | 含义 | 处置 |
|---|---|---|
| 已确认 | 用户与代理对含义、状态和范围一致 | 固定在当前工作版本 |
| 有争议 | 用户陈述与材料冲突，或双方解释不同 | 保留双方版本，进入定向核查或用户确认 |
| 代理推断 | 由多个事实归并出的解释 | 标明推理依据、边界与失效条件 |
| 缺口 | 缺少会改变理解或结论的关键信息 | 优先向用户集中提问；不重要的缺口保留为未知 |
| 决策点 | 下一步需要用户选择的方向或取舍 | 给出选项、依据、风险和未知，不代替用户拍板 |

对齐阶段至少回答：

1. 我们现在知道什么，分别来自哪里？
2. 我们还缺什么，其中哪些会改变当前判断？
3. 有哪些可成立但尚未证实的推断？
4. 下一步有哪些可能，各自依赖什么条件？
5. 哪些内容属于用户决定，不能由代理替选？

高影响问题应集中一次询问。低影响缺口可以保留为未知，不用长问卷换取表面完整。

### 3.3 复盘-对齐循环

每次循环是一个有边界、可复盘的认知版本：

```text
选择本轮目标
  → 复盘新增材料与现有工作态
  → 标出冲突、缺口和推断
  → 与用户做一次集中对齐
  → 确认共同理解、未决项和下一步
  → 判断是否达到本轮关闭条件
```

每轮至少记录：

- 轮次 ID、日期与目标；
- 消费的材料 ID 和版本；
- 工作态发生了哪些变化；
- 哪些认知已对齐，哪些仍有争议；
- 产生了哪些新问题或辅助研究任务；
- 关闭理由与限制；
- 下一轮入口或明确终止条件。

循环可以因“信息足够支持当前用途”而关闭，也可以因时间、材料获取或用户决定而关闭。关闭必须如实记录原因，不能把“找不到”写成“并不存在”。

新增材料不会自动覆盖旧轮次。需要改变已确认内容时，建立新的工作版本；正式输出需要重新绑定新快照。

### 3.4 冻结中间产物

一轮复盘-对齐关闭后，应冻结一份工作快照。快照至少固定：

- 工作模型内容与内容层；
- `as_of`、覆盖期间和范围；
- 材料 ID、物化引用 ID 与哈希；
- 用户确认、代理推断、未知项和争议项；
- 对齐问题和处置结果；
- 允许的用途、受众边界与敏感限制；
- 生成快照所依据的工作版本。

快照是正式输出的唯一内容源。`report/` 中的 Markdown、`document.json`、HTML、DOCX 和 PPT 都属于可再生成的呈现层。

当前实现尚未提供 synthesis 快照与循环事件 CLI；本阶段先在规范中固定语义，具体 schema、路径和命令由后续施工批次决定并回填。

### 3.5 适配输出：中间产物到报告

适配输出先决定“释放什么”，再决定“如何表达”。输出请求至少明确：

| 维度 | 要回答的问题 |
|---|---|
| 受众 | 本人、上级、团队、客户、合作方还是公开读者？ |
| 目的 | 自查、复盘、汇报、争取决策、交接还是说明？ |
| 渠道 | 阅读文档、现场讲解、邮件、网页还是演示？ |
| 时间 | 使用哪个 `as_of` 与覆盖期间？ |
| 范围 | 哪些主题纳入，哪些明确排除？ |
| 敏感边界 | 哪些内容不可披露，是否需要脱敏版本？ |
| 形式 | Markdown、DOCX、HTML、PPT 或其他格式？ |
| 长度与深度 | 一页摘要、完整报告还是分层附录？ |

输出遵循：

```text
Work Snapshot
  → Output Request（受众、目的、范围和敏感边界）
  → DocumentPlan / ExperiencePlan / DeckPlan
  → 格式渲染
  → 实际预览与视觉检查
  → outputs/registry.json 登记
  → 用户要求时进入 publish/packed/
```

不同受众可以改变选材、顺序、详略、语气和表达形式，不能改变同一快照中的事实层、未知项和置信边界。HTML、DOCX 和 PPT 共享同一内容依据；PPT 不能为了版面删除改变理解的关键对照或限制。

涉及外部发布或组织内正式汇报时，受众、敏感边界和可披露范围属于需要用户确认的范围决策。代理可以整理选项和风险，不得擅自扩大披露范围。

## 4. 阶段门

### G1 复盘完成

- 工作主题、目标、状态、进展、结果、阻塞、依赖和下一步在声明范围内可知；
- 每条实质内容有来源层，用户陈述与代理推断没有混写；
- 冲突、缺口与敏感限制已登记；
- 结构化材料可供用户阅读和纠错。

### G2 对齐完成

- 用户与代理对术语、状态、范围和关键因果解释形成一致或明确分歧；
- 高影响缺口已集中询问；
- 代理推断说明了依据和边界；
- 未由用户拍板的决策没有伪装成用户意见；
- 下一步候选与关闭条件清楚。

### G3 快照可用

- 快照绑定工作版本、材料哈希和 `as-of`；
- 快照可离线读取和独立审阅；
- 快照中的事实、推断、未知和争议层完整；
- 新工作态不会静默改写旧快照。

### G4 输出可释放

- 输出请求写明受众、目的、渠道、范围、敏感边界和格式；
- 正式输出绑定快照，而非未冻结模型；
- 每种格式的事实与边界一致；
- HTML/PPT 等视觉成品实际读取预览后登记审查；
- 打包仍然需要用户明确要求。

## 5. 目录与记录映射

| 当前路径 | 职责 | 本设计中的位置 |
|---|---|---|
| `project.json` | 工作区身份与生命周期 | 决定 research/synthesis |
| `brief/provided/` | 用户原始材料与哈希 | 复盘输入 |
| `work-orders/` | 当前工作区拥有的工单 | 工作对象与范围来源 |
| `references/` | 跨工作区物化副本 | 复盘输入 |
| `work-model/model.json` | 当前可编辑工作态 | 复盘与对齐的工作版本 |
| `synthesis/ledger.json` | 循环事件记录 | 复盘-对齐过程真相；追加能力待施工 |
| 工作快照 | 一轮认知的冻结产物 | 正式输出源；路径与 schema 待施工回填 |
| `report/` | Markdown、结构化文档与渲染工作区 | 适配输出 |
| `outputs/registry.json` | 输出、请求、计划和审查登记 | 交付审计 |
| `deliverables/` | 已出稿冻结版本 | 正式交付快照 |
| `publish/packed/` | 用户显式要求后的压缩包 | 发布出口 |

Program 仍只维护下层 workspace/program 的引用与版本 pin，不保存工作模型、对齐结论、报告或快照。

## 6. 各受众的适配原则

| 受众 | 首要目标 | 典型结构 | 必须保留 |
|---|---|---|---|
| 本人自查 | 理解全局并发现缺口 | 工作主题全景、状态、冲突、未知、下一步 | 完整来源层和未决项 |
| 上级汇报 | 快速判断状态与需要支持的事项 | 结论先行、关键结果、风险、决策请求 | 口径、范围、关键限制 |
| 团队协作 | 形成共同上下文并明确分工 | 目标、现状、依赖、责任、下一步 | 争议和未决责任边界 |
| 交接接手 | 让他人无需聊天历史也能继续 | 目标、状态、资料入口、决策链、开放问题 | 材料、快照、未完成事项 |
| 外部交流 | 在授权范围内形成可信说明 | 背景、成果、边界、后续 | 敏感边界、事实与推断分离 |

格式适配不能把“内部自查需要的完整性”直接暴露给所有受众。删减是信息释放决策；保留限制和未知项是事实完整性要求。

## 7. 当前实现边界

已具备：

- `sa.workspace/1` 的 research/synthesis 身份；
- 用户材料登记与哈希校验；
- `sa.work-model/1` 的四层内容模型；
- `sa synthesis init|validate|build` 生成 Markdown、HTML 和可选 DOCX；
- 本地工单、跨工作区引用物化、输出登记与显式打包边界。

尚未完成：

- synthesis 循环事件的 schema、追加命令和状态投影；
- 复盘完整性检查与对齐记录模型；
- 不可变 Work Snapshot 的冻结、校验和输出绑定；
- 输出请求中的选材、脱敏和受众边界机器检查；
- synthesis 到统一 PPT/Deck 流程的完整适配；
- 用户真实材料上的端到端验收。

因此，当前 `sa synthesis build` 只能证明“已结构化的工作模型可以渲染”，不能证明“复盘-对齐循环已经实现”。真实测试不得用机制试点结果替代用户复核。

## 8. 最小验收

1. 用户只提供零散材料时，也能形成带来源层的工作主题、状态和未知项。
2. 每条实质内容可追溯；代理归并不会冒充用户原话。
3. 高影响缺口集中询问一次，未提供的信息保持未知。
4. 用户能够指出并修正工作态，修正产生新的循环记录而不是覆盖历史。
5. 正式输出绑定冻结快照，并写明 `as-of`、覆盖期间、受众与范围。
6. 更换 HTML、DOCX 或 PPT 不改变快照中的事实、未知和限制。
7. 跨工作区引用在本地可读且哈希可校验；权威仍指向原工作区。
8. 未获用户明确要求时不生成压缩包。
