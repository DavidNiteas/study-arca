# 02 · 项目布局

> 本文件是**目录契约的唯一权威**。代码、模板、脚手架都必须与之对齐；改布局先改本文件。

现代工作区使用 `sa.workspace/1`，分为 `research` 与 `synthesis` 两类；身份、共享目录、本地工单和方言的详细字段见 [15](15-工作区身份工单与方言.md)。当前物理根为 `work-root/`；下方 legacy 树继续解释存量项目。

## 0. 新循环布局与兼容（sa.research/1）

新建项目默认 workflow=sa.research/1，新增 research/cycle.json（追加记录）、research/artifacts/<id>/（冻结材料）、research/README.md（导航）。新项目不生成项目级工程四件套；旧项目的 _dev 保留解释历史。下方目录树中的项目 _dev 与 G0–G3 生命周期属于 legacy 布局。

新项目生命周期：active/suspended/archived；研究轮次、讨论后续任务和交付版本在 cycle.json 中分别管理。研究范围修订记录为新 agreement，不覆盖旧约定。同议题新一轮可以在同项目建立 round；范围与数据需要独立管理时可另建项目。

旧项目叠加循环不重写历史 status 或 waiver。research/artifacts 是协议管理的冻结记录，布局、报告等可再生工作目录与其分开。文件路径及记录字段见 [09](09-专业调研循环.md)。

## 1. 仓库总览

```text
study-arca/
├── AGENTS.md                 # 代理薄入口（导航 + 环境绑定）
├── README.md
├── HANDOVER.md               # 经理交接（按内核第三章）
├── _dev/                     # 仓级治理：框架与规范的演进
├── docs/                     # 规范层（见 docs/README.md）
├── src/sa/                   # 框架代码（v0.1）
│   ├── project.py            # 脚手架、来源信封、状态统计
│   ├── evidence.py           # claim/fact/conflict 台账校验
│   └── cli.py                # 子命令实现
│   # 后续按工单增补：fetch/ · store/ · analyze/ · report/
├── scripts/sa.py             # CLI 入口：new / source / lint / status / selftest
├── templates/
│   ├── project/              # 新项目脚手架（含项目级 .gitignore）
│   ├── report/               # 报告骨架
│   └── ppt/                  # 调研 → PPT 大纲模板
└── work-root/                # ▶ 根 .gitignore 忽略；根 program
    ├── program.json
    └── nodes/p-YYYYMMDD-<slug>/
```

> `src/sa/` 的目标结构按工单逐步落地，当前只实现脚手架与校验；未实现的子包不建空目录。

`work-root/` 本身是根 program 仓库；每个 `p-*` 工作区是它的 Git submodule，同时保留独立历史。项目内容不进入产品仓历史。迁移期兼容旧 `workspace/`，新项目默认写入 `work-root/nodes/`。

## 3. 目录职责边界

| 目录 | 只放 | 禁止 |
|---|---|---|
| `brief/` | 用户给的原始需求与约束 | 分析、结论 |
| `search/` | 证据信封 + 原始响应 | 任何加工、改写、编辑后的文本 |
| `analysis/` | 可再生的加工产物 | 交付物、原始证据副本 |
| `report/` | 结构化文档模型与 HTML/Word/PPT 生成物（可再生） | 冻结版本（应放 `deliverables/`） |
| `deliverables/` | 已出稿的冻结快照（带版本与 manifest） | 继续编辑（新版另起目录） |
| `publish/` | 对外成品：版本目录、`release/` 最新副本；`packed/` 仅在用户要求打包时使用 | 底稿、脚本、中间图、内部评审材料、自动生成的 zip |
| `tools/` | 项目专用代码 | 通用能力（应升格到 `src/sa/`） |
| `_dev/` | 治理文档 | 数据、报告正文 |

**`report/` 与 `deliverables/report/` 的分工**：`report/` 是渲染工作区，删掉后能由 `analysis/` + `document.json` 重建；`deliverables/report/vX/` 是冻结交付件，只读、带 manifest。两者不互抄，避免双写。

**可再生原则**：删掉 `analysis/` 与 `report/` 后，应能凭 `search/` + `tools/` 复现结论与渲染；做不到，说明加工或渲染过程没有被记录。

## 4. 命名与 ID

| 对象 | 规则 | 例 |
|---|---|---|
| 项目目录 | `p-<YYYYMMDD>-<kebab-slug>` | `p-20261020-ai-chip-market` |
| 来源 | `s-<4 位序号>-<短 slug>`，序号项目内递增、**不复用** | `s-0007-cnnic-report` |
| 结论 | `c-<4 位序号>` | `c-0012` |
| 基准事实 | `f-<4 位序号>` | `f-0003` |
| 冲突 | `x-<4 位序号>` | `x-0002` |
| 交付版本 | `v<major>.<minor>`；G3 出稿为 `v1.0` | `deliverables/report/v1.0/` |
| 子问题 | `q<n>-<slug>` | `q2-supply-chain` |

slug 用小写英文与连字符；标题用中文。ID 一旦分配，删除后也不得复用——缺口本身是审计线索。

## 5. `tools/` 的晋升与降级

- 项目脚本允许粗糙，但必须能从 `_dev/04` 找到"谁在什么时候为什么写的"。
- **晋升判据**：被第二个项目复用，或需要长期维护 → 开仓级工单收进 `src/sa/`，项目内只留薄封装，`03` 登记"承接"关系。
- **禁止**：为单个项目在框架里加特例分支；项目脚本 import 框架内部模块。

## 6. 大文件与二进制

- `search/*/raw/` 默认忽略：PDF、大 CSV、图片、网页快照不进项目 git。
- 需要版本化的证据用 `extracted.md`（规范化文本，含定位符与关键摘录）。
- 确需入库的原始件 ≤ 1 MB 且为文本时，可 `git add -f`，并在 `meta.json` 的 `raw` 里登记 sha256。
- 禁止把整个数据库导出直接塞进 `analysis/datasets/`；只保留分析实际用到的切片，并写清筛选条件。

## 7. 项目生命周期

```text
scoping(G0) ─► collecting(G1) ─► analyzing(G2) ─► delivered(G3) ─► archived
     │                                              │
     └──────────── suspended ◄──────────────────────┘
```

- 状态以 `project.json.status` 为机器可读真相，以 `_dev/03` 为人读真相；两者由 `sa lint` 校验一致。
- 交付后项目**不删除**：`project.json.status = archived`，目录保留，供后续引用（类似归档工单）。
- 同一议题的后续调研**新开项目**，在 `01` 里写"承接自 p-xxx"，不原地复活旧项目。
