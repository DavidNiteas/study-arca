# 18 · 报告编排与输出

中文 | [English](en/18-report-orchestration.md)

> 本文定义独立报告从 Synthesis 原料中选择内容、形成叙事并输出 DOCX、HTML、PPT 的业务契约。报告复用现有 DocumentPlan、ExperiencePlan、DeckPlan 和输出登记机制，不另造平行呈现系统。
>
> 状态：D7 第一层已实装；`sa report` 支持 ReportPlan、来源校验、ReportDocument、DOCX/HTML/PPT 构建和统一输出登记。`sa synthesis build` 继续作为兼容工作汇总入口。

## 1. 定位

报告不是 snapshot 的自动渲染视图，而是一个独立的小型研究设计与表达产物。

Synthesis 中的工作模型、knowledge/design baseline、alignment、材料和研究过程是报告原料。报告可以选择一个或多个冻结来源，也可以不引用某些 Synthesis 内容；未采用的内容不需要进入报告正文或来源索引。

以下关系不可颠倒：

```text
Synthesis 工作与设计
  ≠ 报告

Synthesis 工作与设计
  → 可选择、压缩和重组的报告原料
  → 报告
```

`sa synthesis build --snapshot` 是兼容的工作汇总快捷入口，不等同于正式报告流程。

## 2. 输出链

```text
冻结来源
  → ReportBrief
  → ContentMap
  → NarrativePlan
  → ReportDocument
  ├─ DocumentPlan  → DOCX
  ├─ ExperiencePlan → HTML
  └─ DeckPlan       → PPTX
  → 实际预览与审查
  → outputs/registry.json
```

## 3. ReportBrief

ReportBrief 描述“这次为什么做报告、给什么场景使用”。字段按报告性质选用，不设置统一必填门槛。

可包含：

- 受众；
- 使用场景；
- 目的；
- 长度或时间限制；
- 展示渠道；
- 披露范围；
- 风格或形式要求；
- 其他本次特有约束。

没有提供的字段不伪造。报告计划应记录本次实际采用的约束、默认假设和未指定项。

### 3.1 报告工作区

正式报告按 ID 独立存放：

```text
report/
└── <report-id>/
    ├── plan.json          # sa.report-plan/1
    ├── document.json      # sa.document/1
    ├── plans/
    │   ├── docx.json      # sa.document-plan/1
    │   ├── html.json      # sa.experience-plan/1
    │   ├── pptx.json      # sa.deck-plan/1
    │   └── pptx-layout.json
    ├── artifacts/
    ├── previews/
    └── manifest.json      # 本报告内部 artifact 的 ID/path/SHA-256 索引
```

旧 `report/work-summary.md`、`report/document.json`、`report/index.html` 和 `report/report.docx` 继续由兼容入口使用，不强行迁移。

### 3.2 ReportPlan 最小结构

```json
{
  "schema": "sa.report-plan/1",
  "id": "rpt-0001",
  "project": "p-example",
  "title": "报告标题",
  "as_of": "YYYY-MM-DD",
  "formats": ["docx", "html", "pptx"],
  "brief": {},
  "sources": [],
  "content_map": [],
  "narrative": {
    "core_question": "",
    "angles": [],
    "sections": []
  },
  "assumptions": [],
  "open_issues": []
}
```

`formats` 是实际生成目标，至少一项。`brief` 的字段按报告性质选用；`narrative.sections[].id` 是 ContentMap 的稳定目标。

## 4. 冻结来源

报告可以使用以下来源：

- 一个或多个 `sa.work-snapshot/1`；
- `brief/provided/` 中的材料；
- `references/` 中的物化引用；
- `design_artifact` 记录；
- `alignment` 记录；
- 用户明确提供、已经登记的其他来源。

每个被报告直接采用的来源必须有稳定 ID、来源类型和校验信息。报告不得直接读取渲染时仍在变化的 `work-model/model.json` 或未冻结工作态。

报告来源与程序内部调研线索不是同一个概念。Synthesis 中用于形成判断但未进入报告的材料，不必出现在报告来源列表中；反之，报告中每个可追溯事实都应能返回其冻结来源。

| `kind` | `ref` 指向 |
|---|---|
| `snapshot` | `synthesis/ledger.json` 中的 snapshot ID |
| `material` | `brief/provided/manifest.json` 中的 `u-NNNN` |
| `reference` | `references/index.json` 中的 `ref-NNNN` |
| `design_artifact` | synthesis ledger 中的 `design_artifact` ID |
| `alignment` | synthesis round ID，取该轮 alignment 记录 |

报告中的引用 ID 使用 `s-NNNN`，并在 ReportPlan 的 `footnotes` 中描述其报告内意义。`content_map[].source_ref` 指向这些 `s-NNNN`，而不是直接写文件路径。

## 5. ContentMap

ContentMap 是报告编排的核心。它记录报告原料如何被选择、变形和释放，而不是简单复制来源清单。

每条映射至少包含：

```text
source_ref
source_item
disposition
target_sections
release_level
detail_level
rationale
```

`disposition` 至少支持：

- `include`：原样或近原样采用；
- `compress`：压缩为摘要或关键判断；
- `omit`：不进入报告；
- `redact`：脱敏后采用；
- `defer`：本次不采用但保留后续使用可能。

`release_level` 和 `detail_level` 的具体取值由项目、报告性质或方言定义，不写死统一等级。

不是每个 Synthesis 源项都必须出现在 ContentMap 中。报告只需记录实际考虑过的候选、被采用的内容、影响理解的显著省略和不可披露内容。省略重要反证、未知或关键限制时必须有理由。

## 6. NarrativePlan

NarrativePlan 在动笔和排版前确定报告如何被理解：

- 核心问题；
- 主要叙事角度；
- 核心主张或其问题形式；
- 章节或页面级脉络；
- 每节承担的解释任务；
- 可以释放什么；
- 不能释放什么；
- 说到什么详细程度；
- 哪些证据必须与主张同时出现；
- 哪些未知、反证和限制不能被版面优化删除。

同一 ReportDocument 可以派生 HTML、DOCX 和 PPT，但不同媒介可以调整篇幅、顺序、视觉节奏和交互方式。事实、未知、边界和披露限制不得因媒介变化。

## 7. ReportDocument

ReportDocument 复用 `sa.document/1`，是格式中立的内容源。

它至少保留：

- 章节和块结构；
- 内容层；
- 来源与脚注；
- 关键未知和限制；
- 设计状态说明；
- 对应的 ReportPlan ID 和版本；
- 实际采用来源的哈希。

报告计划自身、ReportDocument、各格式计划和最终产物都应有稳定 artifact ID 和 SHA-256。

## 8. 格式适配

### 8.1 DOCX

由 `ReportDocument → sa.document-plan/1 → DOCX`。

适用于正式阅读、审阅、批注和归档。

### 8.2 HTML

由 `ReportDocument → sa.experience-plan/1 → HTML`。

适用于离线阅读、搜索、内容分层和来源查看。

### 8.3 PPTX

由 `ReportDocument → sa.deck-plan/1 → PPTX`。

PPT 复用调研呈现规范：

- 先确定叙事角度与页面主张；
- 按内容关系选择原创图解；
- 生成 RenderLayout；
- 实际编译 PPTX；
- 生成逐页预览；
- 读取预览并记录视觉审查；
- 修订后重新构建和复查。

不能因为页面空间不足删除理解所必需的对照、证据边界或限制。

## 9. 输出登记

所有正式输出进入 `outputs/registry.json`，包括 DOCX、HTML 和 PPTX。

D7 已把输出 registry 的 artifact 解析从仅支持 research cycle artifact 扩展为按 workspace 类型解析：

```text
research  → cycle artifact
synthesis → report plan / ReportDocument / format plans / outputs / previews
```

登记至少绑定：

- project；
- report ID；
- source snapshot(s)；
- ReportDocument；
- format plan；
- 最终产物；
- 预览；
- 审查状态和审查方式；
- 生成时间。

## 10. CLI 目标

正式报告的首层操作为：

```powershell
sa report init <project> --id <report-id> --title <title>
sa report validate <project> --id <report-id>
sa report document <project> --id <report-id>
sa report build <project> --id <report-id> --format docx|html|pptx
sa report register <project> --id <report-id> --format docx|html|pptx
sa report status <project>
sa report archive <project> --id <report-id> --before v1.0
sa report archive <project> --id <report-id> --before v1.0 --apply
sa report archive <project> --id <report-id> --before v1.0 --verify
```

底层继续复用：

- `sa document convert|validate|build`；
- `sa experience convert|validate|build`；
- `sa deck convert|validate|build|preview`；
- `sa output apply|status|lint`。

`report build` 与 `report register` 的 `--format` 可重复，用于一次处理多个格式。`report register --preview <path>` 可把实际预览登记为报告 artifact；审查事件继续按统一输出登记契约追加。

`report archive` 处理的是被新发布阶段取代的开发历史，不是对外发布包。它默认输出计划；`--apply` 时把早于 `--before` 的版本产物和摘要预览写入项目 `archive/`，验证后删除旧源；`--verify` 复核已有归档。当前版本、评审材料、交付快照和 `publish/` 不受影响。压缩包默认不入 Git，manifest 保留校验与恢复索引；Git 历史压缩是另一项显式维护动作。

## 11. 兼容与边界

- `sa synthesis build --snapshot` 保持兼容，继续生成固定工作汇总；
- 新正式报告不得依赖该固定汇总作为唯一内容；
- 一份报告可以使用多个冻结来源，不要求单一 snapshot；
- 打包仍是独立用户动作；
- 预览成功不代表看过，机器检查不等于视觉审查；
- 未指定受众或披露字段不等于允许任意披露；报告 nature、组织授权和首席研究员决定仍然生效。
