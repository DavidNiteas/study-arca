# 12 · 系统定位与能力管理

Study Arca（仓库名 `study-arca`，原名 search-analysis）是面向人类—代理调研互动、可持续沉淀研究能力的系统。其目标交付单元是一份可独立运作、自包含的研究工作区；工作流、技能、代码工具与环境配置共同支撑这一目标。

母系统沉淀通用方法与能力，负责生成、维护和演进工作区；每份工作区保存自己的研究问题、证据、讨论、状态、成果及运行所需能力，支持迁移与交接。

自包含的目标验收是：将工作区迁移到另一位置，交给未参与前序对话的代理，能够理解目标、恢复所需环境并继续工作。外部服务和凭据依赖需显式说明；不将原机器路径、母仓隐含依赖或聊天记忆视为工作区自带能力。

**当前边界**：项目已有独立 Git 仓库和研究记录，但规范、部分技能与公共 CLI 仍依赖母仓。能力随附、版本锁定、更新机制及脱离母仓的迁移验证尚未实现；本次更名只明确方向，不表示上述能力已经完成。

## 职责与权威

| 组成 | 职责与位置 | 边界 |
|---|---|---|
| 调研工作流 | docs/ 定义五域循环、证据与交付；项目 research/cycle.json 记录问题、反馈、行动和回答 | 业务不自动套用工程工单；规范描述与机器能力区分 |
| skill 流程集合 | .agents/skills/ 引导代理按任务读取规范、选择方法、执行与交接 | skill 是执行入口，业务权威在 docs/；不重复维护 schema |
| 代码工具 | src/sa/ 与 scripts/sa.py 提供可重复执行的公开能力；项目 tools/ 存领域适配 | 项目仅依赖公开接口；实验验证不等于通用工具已经集成 |
| 环境管理 | AGENTS.md 绑定平台；任务记录实际依赖、渲染器、字体、模型读图能力和限制 | 当前为能力记录与运行检查，不是统一环境安装/探测管理器 |

人类定义目的与边界、参与讨论与范围修订；代理在授权范围内调研、分析、设计、执行和反馈。具体授权与记录契约见 [09](09-专业调研循环.md)。模型或供应商不是工作流的隐含前提；执行前验证实际能力。

## 能力状态与运行记录

能力描述至少区分：已集成公共工具、项目级已验证适配、尚未验证/不可用。记录验证时间、环境/依赖版本、入口、实际验证方式、失败点、复现材料以及回退方式；不在环境记录中保存密钥。

呈现任务可在设计意图的环境段记录：内容/布局格式，渲染器版本，字体与关键依赖，输入输出路径，图像读取是否实际成功，审查方式。安装或改变全局配置不是“存在规范”就自动获得授权；遵循当次任务授权。

当前：HTML/DOCX 有公开 render 子命令；PPT 内容/布局 LR 与 PowerPoint 实际渲染在杀菌剂项目验证，`sa render pptx` 尚未集成。原生 PPT 路径不保证其他软件显示一致；缺目标环境时说明限制与待办，不登记视觉通过。前端 CDP 循环可借鉴同样的反馈方法，但本仓不宣称已实现通用网页渲染接口。

## 沉淀路径

项目反馈 → 问题/后续行动 → 当地验证 → 可迁移经验 → 框架工单 → 更新规范、技能或公共工具 → 回到项目复验。

- 方法经验进入设计案例与规范，见 [11](11-PPT设计方法与模式.md)。
- 重复且稳定的机械操作才抽为代码；保留输入输出、失败语义与兼容约束。
- 环境失败形成能力记录，不把一次成功推断成所有模型、平台都可用。
- 根仓负责通用体系，项目独立仓保存证据与成果；不把 workspace 纳入根仓或 submodule。

新代理从 [10](10-代理工作协议.md) 接手；能力缺口、未决问题和下一步归属须随交接保存，而不是留在聊天记忆中。
