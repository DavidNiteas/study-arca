# 15 · 工作区身份、工单与方言

> 本文件定义 `sa.workspace/1`、`sa.program/1`、本地工单、用户材料、引用和工作区方言契约。当前物理根为 `work-root/`；旧 `workspace/` 仅作迁移兼容。

## 1. 工作区身份

现代工作区在根 `project.json` 中声明：

```json
{
  "schema": "sa.workspace/1",
  "id": "p-20261103-example",
  "workspace_type": "research",
  "workflow": "sa.research/1",
  "status": "active"
}
```

| 类型 | workflow | 主对象 |
|---|---|---|
| `research` | `sa.research/1` | 问题、来源、证据、claim/fact/conflict |
| `synthesis` | `sa.synthesis/1` | 用户当前工作状态、材料、归纳、缺口 |

身份以元信息为准，不由目录名决定。缺少 `schema` 的存量 `p-*` 工作区按 legacy 解释；只有 `workflow=sa.research/1` 时推断为 research。

## 2. 标准布局

共享目录：

```text
brief/
  brief.md
  inbox/
  provided/
    manifest.json
dialect/
references/
work-orders/
report/
outputs/
deliverables/
publish/
```

Research 追加：

```text
search/
tools/
analysis/
research/
```

Synthesis 追加：

```text
work-model/
synthesis/
```

Synthesis 可以按需创建 `research/` 作为辅助研究，但辅助研究不能改变工作区类型。

`brief/inbox/` 是新项目提供的用户投递暂存区：用户可以先把文件或目录放进去，也可以直接告诉代理路径。暂存内容尚未登记，不进入工作模型、分析或渲染；代理盘点并经用户确认后，通过 `sa input add` 复制到 `brief/provided/u-NNNN/`。inbox 内容由项目 `.gitignore` 排除，避免把未登记或敏感材料误提交。

## 3. 本地工单

工单文件位于宿主工作区的 `work-orders/wo-NNNN.json`：

```json
{
  "schema": "sa.work-order/1",
  "id": "wo-0001",
  "owner_workspace": "p-20261103-example",
  "title": "任务标题",
  "status": "active",
  "created": "2026-11-03",
  "goal": "要达成的目标",
  "scope": [],
  "acceptance": [],
  "references": []
}
```

- `owner_workspace` 必须等于宿主工作区 ID。
- 工单只属于一个工作区。
- 其他工作区引用工单时，必须在自己的 `references/` 中保存不可变副本。
- Program 不拥有工单，也不复制工单正文。

```powershell
python scripts/sa.py work new <project> --title "..." --goal "..."
python scripts/sa.py work list <project>
python scripts/sa.py work status <project> --id wo-0001 --status active
```

## 4. 用户提供的材料

`brief/provided/manifest.json` 使用 `sa.provided-inputs/1`：

```json
{
  "schema": "sa.provided-inputs/1",
  "items": [
    {
      "id": "u-0001",
      "path": "weekly-report.md",
      "role": "work_record",
      "authority": "first_person",
      "verification": "self_reported",
      "sha256": "…"
    }
  ]
}
```

`role` 为 `constraint/context/work_record/evidence/hypothesis`。用户提供不等于外部事实已核验；该状态由 `verification` 单独表达。

```powershell
python scripts/sa.py input add <project> --file <path> --role work_record
```

该命令把文件复制到 `brief/provided/u-NNNN/` 并写入哈希；不会修改原文件。

## 5. 跨工作区引用

`references/index.json` 使用 `sa.references/1`。引用关系限定为：

- `context_from`
- `evidence_from`
- `derived_from`
- `supersedes`
- `related_to`

只有 `related_to` 可以作为纯导航。任何进入分析、汇总或渲染的内容都必须复制进当前工作区并校验副本哈希。副本便于本地迁移，但过程、证据等级和可信度权威仍在目标工作区。

## 6. 方言

| 层 | 位置 | Git |
|---|---|---|
| Core | 产品源码 | 追踪并发布 |
| User dialect | Study Arca 根 `dialect/` | 不追踪、不发布 |
| Workspace dialect | `<workspace>/dialect/` | 随工作区追踪 |

优先级：Core 硬约束 > Workspace dialect > User dialect > Core 默认值。

影响正式内容、验收或输出的 User dialect 依赖必须物化到 Workspace dialect。通用能力只能通过显式晋升进入 Core：

```text
Workspace dialect → User dialect → Core
```

用户级方言可从模板初始化：

```powershell
python scripts/sa.py dialect init
python scripts/sa.py dialect status [--workspace <workspace>]
python scripts/sa.py dialect import --workspace <workspace> --source <dialect.json>
python scripts/sa.py dialect promote --workspace <workspace> --scope user
python scripts/sa.py dialect promote --workspace <workspace> --scope core --output <proposal-dir>
```

晋升不会自动修改发布核心。`core` 模式只导出带文件哈希的 draft 提案，后续必须经过
开发工单、去个人化整理、测试和经理终审。

当前实现只负责方言资产的管理、隔离、导入和晋升提案；方言扩展点的实际加载执行与
多方言冲突解析尚未实现，不能把“已登记能力”理解为“运行时能力已经生效”。

## 7. 兼容

- 存量 `p-*` 未声明 `schema/workspace_type` 时按 legacy 解释。
- `sa new` 新项目默认 research；`--type synthesis` 创建总结型工作区。
- `workspace/` 到 `work-root/` 的本地迁移已完成；旧路径不再作为默认根。

## 8. Program v1

Program 使用 `program.json` 和 Git submodule：

```json
{
  "schema": "sa.program/1",
  "id": "prog-example",
  "title": "示例 program",
  "status": "active",
  "distribution": "local"
}
```

- 子节点固定位于 `nodes/<node-id>/`。
- `.gitmodules` 保存子节点 URL，gitlink 保存 pin 提交。
- Program 不保存工单、证据、状态副本或输出。
- 默认 `local`；`cloneable` 必须通过根远端、所有递归子节点远端和 pin 可达检查。

```powershell
python scripts/sa.py program init <path> --id prog-example --title "示例"
python scripts/sa.py program attach <program> <workspace>
python scripts/sa.py program status <program>
python scripts/sa.py program check <program> --require-cloneable
python scripts/sa.py program set-distribution <program> cloneable
python scripts/sa.py program index <program>
python scripts/sa.py program clone <source> <destination>
python scripts/sa.py program bundle <program> --output <bundle.zip>
```

Program 初始化时会携带 `bin/program.ps1` 和 `bin/program.sh` 薄启动壳；脚本优先使用
`SA_HOME`，否则从脚本位置向上寻找 `scripts/sa.py`。

`program clone` 使用 staged clone，递归校验通过后才落位。`program bundle` 只接受
干净、已提交的 program 树，并把完整 `.git` 对象和工作树打成离线迁移包。

## 9. Synthesis 工作模型

Synthesis 的当前状态保存在 `work-model/model.json`，使用 `sa.work-model/1`。
每个工作主题包含目标、状态、进展、结果、阻塞、已计划事项和材料 ID。材料只能引用
`brief/provided/` 或 `references/` 中已登记的对象。

复盘、对齐、复盘-对齐循环、冻结快照和适配输出的完整业务契约见
[16](16-复盘对齐与适配输出.md)。本节只描述当前已经落地的数据结构。

具体内容项可以写成：

```json
{
  "text": "完成接口评审",
  "layer": "material",
  "materials": ["u-0001"]
}
```

`layer` 只允许 `user_statement`、`material`、`inference`、`unknown`。兼容旧字符串时
默认视为 `user_statement`。报告生成必须直接构造显式层，不得用文本启发式把材料或
未知项重新归类为事实。

```powershell
python scripts/sa.py synthesis init <project>
python scripts/sa.py synthesis validate <project>
python scripts/sa.py synthesis status <project>
python scripts/sa.py synthesis apply <project> --file <records.json>
python scripts/sa.py synthesis snapshot <project> --round r-0001 --id snap-0001 --label "..."
python scripts/sa.py synthesis alignment <project> --round r-0001
python scripts/sa.py synthesis build <project> [--snapshot snap-0001] [--docx]
```

`synthesis apply` 追加复盘、问题、回答、修正和对齐事件；轮次关闭后，
`synthesis snapshot` 把当前工作模型冻结为不可变快照。`synthesis build` 从模型或
指定快照生成 `report/work-summary.md`、`report/document.json` 和自包含 HTML；
加 `--docx` 时同时生成 Word。正式输出应使用 `--snapshot`。生成器不会补写模型中
没有的成果、计划或因果关系。
